Architecture review remote-factory 28 Jul 2026 incl. PR #1051 · #1052

Distributing the factory workflow engine

The graph IR is already the right abstraction. What's single-machine is the interpreter — execution position on a Python call stack, artifacts on a local filesystem, agents as local subprocesses. Here's what that costs, what the in-flight PRs reveal about it, and how a durable-execution engine maps onto every existing primitive.

Current state

You already have a compiler front-end

factory/workflow/primitives.py + definitions.py is a typed graph IR that's independent of how it runs — and it already has two back-ends: executor.py walks it for headless runs, skill_export.py compiles it to prose for the CEO agent. That design decision is what makes this whole proposal cheap. Nothing about the graph model needs to change.

Where it breaks

Eight single-machine assumptions

These live in the interpreter, not the graph. Each is annotated with whether a durable-execution engine resolves it outright, or whether it needs work from you regardless.

Execution position lives on the Python call stack
_execute_from() recurses along edges; progress state (completed_files, node_context, iteration_counts) is instance memory. A crash loses the entire run. checkpoint.py exists but serves only the CEO path — the executor never touches it.

Read this ledger as a sequence, not a list

Three of the eight are prerequisites you owe yourself regardless of which engine wins: real artifact I/O, gate determinism, and idempotent finalize. Do those and the single-machine executor gets better too. Skip them and no orchestrator can help you, because retries will corrupt experiment state.

In flight

What PRs #1051 and #1052 are actually telling you

Both PRs are building toward nested orchestration — an outer loop that observes and steers inner factory cycles. Read together, they're an independent rediscovery of the same problem this proposal addresses, solved with the tools currently available.

#1051 — InnerLoop + CycleAnalyzer

InnerLoop.step() is a model.forward()-shaped interface: it shells out to factory ceo --mode evolve --no-worktree as a subprocess, then reconstructs what happened by parsing .factory/ artifacts. CycleAnalyzer does the reconstruction across four tiers — events.jsonl for agent steps and costs, results.tsv for verdicts and scores, experiment dirs for eval artifacts, and the workflow definition for DAG provenance.

The load-bearing observation

CycleAnalyzer is a post-hoc execution ledger, reverse-engineered from files a run happened to leave behind. Its NodeTrace dataclass literally re-joins declared reads/writes against artifacts that exist on disk, guessing at what ran. In a durable-execution engine that ledger is the workflow history: typed, complete, queryable, and produced without a single extra line of instrumentation.

The PR's own "How to consume InnerLoop" section poses Path A (Python optimizer) vs Path B (agent optimizer as a factory mode) vs Path C (hybrid) as an architectural fork. That fork dissolves under a durable engine: the outer loop is a parent workflow, the inner cycle is a child workflow, and whether the parent's decision step is Python or an LLM agent becomes an ordinary node-type choice inside it — not a different integration architecture. You get Path A's programmatic control and Path B's agent reasoning in the same structure.

#1052 — optimize mode + pre_eval/post_eval

The optimize workflow is a run→collect→reflect loop over a target mode, driving evolve on a separate project. Two details are diagnostic:

  • pre_eval and post_eval are pure instrumentation nodes. The PR body is explicit — pre_eval copies current_score.json to eval_before.json "giving CycleAnalyzer a before-snapshot"; post_eval emits an eval.completed event "enabling CycleAnalyzer._extract_scores()". These are DAG nodes added so a downstream component can reconstruct execution state. That's the graph paying rent for a missing ledger. Under an engine with real history, both nodes are deletable.
  • --focus "mode:project_path:benchmark" is a workflow input struct encoded as a colon-delimited string. Typed workflow inputs are free in every engine under consideration. This is a small thing that will get painful fast as outer-loop configuration grows.

Also worth flagging for the review itself: #1052 carries #1051's nine commits plus its own, and its diff touches definitions.py at +829/−184 against #1051's +447/−0. The stacking means the two can't be evaluated independently — and both branches reintroduce a stray top-level workflow-evolve/SKILL.md alongside the correct skills/workflow-evolve/SKILL.md, which looks like an artifact of running the exporter from the wrong cwd.

Recommendation on sequencing

Don't block these PRs on the orchestration work — they encode real domain knowledge about what an outer loop needs to observe, and that knowledge is exactly the requirements document for the durable-execution port. But treat CycleRecord as the target schema, not CycleAnalyzer as the permanent mechanism. Keep the dataclasses; expect the file-scraping implementation behind them to be replaced by history queries.

Premise check

Distribution does not cost you prompt caching

Anthropic prompt caching is server-side, keyed on exact prefix bytes and scoped to your API key and organization, with a 5-minute default TTL (1 hour extended). It is not machine-local. Spreading steps across workers does not, by itself, lose a single cache hit.

What does cost you cache hits:

Real cache risks, ranked
RiskMechanismFix
Prefix instability resolve_prompt() composes the prompt at call time from machine-local state: base prompt + ~/.factory/playbooks/<role>.md (ACE-evolved) + ~/.factory/profile.md + skills/workflow-*/SKILL.md. A different worker with a different playbook version emits different bytes — a guaranteed miss. Resolve the prompt bundle once per run, content-hash it, ship it as a run artifact. Worth doing today, independent of any of this.
TTL gaps Same-role steps scheduled far apart fall outside the cache window. Extended 1h TTL; schedule same-role work adjacently on the same queue.
Session continuity Claude Code's --resume and ~/.claude transcripts are machine-local. Non-issue today: every invoke_agent is a one-shot claude -p with --append-system-prompt-file. You are already stateless per agent call. Only matters if you later want multi-turn agents, which needs worker affinity.

So the actual cost of distribution is the workspace — the git tree and .factory/ — not the cache. That reframes the whole design problem, and it's the subject of the first tradeoff below.

Proposal

Temporal as a third back-end, not a rewrite

Add factory/workflow/temporal/ containing a deterministic interpreter of the existing graph — a third consumer of the IR alongside WorkflowExecutor and skill_export. definitions.py is untouched. Both interpreters ship in parallel until parity is proven against the existing --dry-run path and benchmark suite.

Scaling steps individually falls out natively

One task queue per role, each with independently sized worker pools and its own max_concurrent_activities. This is the requirement you opened with, and it needs no new mechanism.

Amber chips share a workspace and must land on the same worker — see the workspace tradeoff below.

Two constraints that will bite

  • Payload size. Agent stdout runs to megabytes. Never return it into workflow state — return an artifact URI plus a small verdict struct. Temporal caps payloads at 2 MB and history at 50 MB, and result.node_outputs[node_id] = output in today's executor stores full stdout in memory for every node.
  • Determinism versioning. A graph edit mid-run breaks replay. Pin the graph definition hash into the workflow input so a running execution keeps its graph, and use workflow.patched() for interpreter changes. Note this interacts directly with optimize mode from #1052, whose entire purpose is mutating workflow definitions — running optimizations must not adopt a graph mid-flight.

Tradeoff · expanded

How aggressive should the workspace refactor be?

This is the real cost of distribution. Steps communicate through .factory/* files and a git working tree; on one machine that's free. Three postures, with what each actually buys.

Before comparing them, the fact that decides it: look at what each node's reads/writes actually touch. In improve_workflow, the shared prefix — study → researcher → gate_research → strategist → gate_strategy — touches only .factory/strategy/*.md. It is artifact-only and can run anywhere. The per-hypothesis loop — builder → health_checker → code_reviewer → adversarial_tester → gate_precheck — needs the actual git working tree, because QA reads the diff. The natural fault line is exactly the SubgraphForkNode boundary that already exists in the graph.

Worker-affine everywhere minimum change

An allocate_workspace activity returns the worker's unique task-queue name; every subsequent activity in the run is scheduled to that queue, so it hits the same worker and the same worktree.

+Zero artifact-transport work. Current filesystem semantics preserved byte for byte.
+Fastest path to durability — you get crash-resume and retries this month.
−You can only scale whole runs, not steps. This does not solve your stated problem.
−A worker restart strands the workspace; recovery means re-running the whole branch.
−Container sizing becomes worst-case: every worker must be big enough for builder.
Right answer only if durability, not scale, is the near-term goal.

Full content-addressed artifacts maximum change

Every node materializes its declared reads from an object store before running and uploads its writes after, returning content hashes. Workers are fully stateless.

+True per-step scaling and heterogeneous container sizes. Any worker runs any step.
+Turns the reads/writes declarations into enforced, tested reality — a correctness win on its own.
−The builder/QA loop needs the working tree, so this means shipping git state on every hop — expensive and slow for large repos.
−Requires every node's declarations to be complete and accurate. They currently aren't verified against runtime behavior.
The right end state, the wrong starting point.

Hybrid — sticky branches, artifact prefix recommended

Split at the fault line the graph already draws. The shared prefix and cross-branch coordination go artifact-based and fan out freely. Within a hypothesis branch, steps stay pinned to one worker and one worktree. Code moves between branches via git push to a bare remote — machinery worktree.py already half-implements.

+Parallelises exactly what's expensive: research fan-out, N-hypothesis branches, and outer-loop optimize runs driving many targets.
+Container sizing per queue — cheap boxes for research and archival, large ones only on build-q.
+You only need accurate reads/writes for prefix nodes to start — a much smaller correctness surface than the full refactor.
−Two workspace modes to reason about; a node's placement is now part of its contract and needs to be declared on the node.
−Branch-internal failures still cost a whole-branch replay, not a single-step retry.
Verdict: take this. It gets you real per-step scaling where it pays, without pretending the QA loop can be stateless. Add a workspace: "shared" | "sticky" field to Node and let the validator enforce that a sticky node never reads an artifact-only predecessor's output without an explicit materialization edge.

Tradeoff · expanded

Does the CEO path come along?

Context for the choice: today factory ceo is the primary entry point. It launches an interactive Claude Code session with ceo.md as system prompt, the agent reads the matching SKILL.md, and follows it as prose — spawning specialists via factory agent <role>. The headless WorkflowExecutor is the secondary path, used by benchmarks and --headless runs. That means the two paths have different reliability characteristics today, and any orchestration work applied to one widens that gap.

Note also that InnerLoop.step() in #1051 drives the CEO path, not the executor — it shells out to factory ceo --mode evolve. So the outer-loop work currently depends on the path that would be left behind.

Headless executor only smallest blast radius

Temporal backs factory workflow run. factory ceo is untouched and keeps working exactly as today.

+No change to the 2.3k-line cli/ceo.py, no risk to the primary user-facing flow.
+Benchmarks and CI runs — the workloads that most need scale — benefit immediately.
−The capability gap widens permanently: durable, scalable, observable headless runs versus a best-effort interactive path.
−#1051's InnerLoop keeps shelling out to the un-orchestrated path, so outer-loop work gains nothing.
−Two divergent implementations of the same 16 workflows to keep semantically aligned. This is already a maintenance cost; it grows.
Defensible only if you expect the CEO path to be deprecated.

CEO becomes a Temporal client unifying

factory ceo starts a workflow and drives user gates via signals; the interactive session becomes a presentation layer over durable execution.

+One execution model. evaluator_type="user" gates become genuinely meaningful in both paths.
+Interactive runs gain crash-resume — today a closed terminal loses a multi-hour cycle.
+The dashboard reads workflow history instead of tailing events.jsonl.
−Substantial rewrite of cli/ceo.py, and it changes the CEO's felt behaviour — the agent stops being the orchestrator and becomes a participant. That is a product decision, not just an engineering one.
−The SKILL.md prose playbooks lose their reason to exist in their current form, which is a large amount of committed, reviewed work.
The right destination — but not a first move.

Headless first, CEO retrofitted as a declared phase recommended

Ship the headless interpreter now, but design the gate and signal API on the assumption the CEO will become a client. Concretely: define the human-gate protocol (signal names, verdict payload shape, timeout semantics) in phase 1 even though only the headless path uses it, and keep skill_export generating SKILL.md from the same graph so the two never drift on step ordering.

+Small first move, but no rework when the CEO migrates — the API it needs already exists and has been exercised.
+Lets you decide the CEO's fate with evidence, after seeing how the headless path behaves under real load.
−You carry two paths for a defined interval, and "defined" requires discipline — write the deprecation criterion down now.
Verdict: take this, and make the phase-3 trigger explicit: migrate the CEO once the headless path has run the full improve workflow end-to-end at parity for some agreed number of cycles.

Comparison

Engine alternatives

Weighted against your stated constraint: containerized, but not tied to Kubernetes or OpenShift primitives. That constraint does real work here — it demotes the K8s-native options that would otherwise be strong, since their scheduling model is the cluster's.

Assessed against cyclic gates, long agent runs, human waits, and container-agnostic deployment
EngineFitAssessment
Temporal recommended Cyclic RELOOP semantics need real code, not YAML. Multi-hour activities and indefinite human waits are its core case. Per-queue scaling maps 1:1 onto "scale steps individually." Workers are plain containers — no cluster primitives required, runs anywhere containers run. Cost: a server plus a datastore to operate, and the determinism discipline.
Restate strong runner-up Best developer experience for durable handlers and human-in-the-loop; single binary, materially lighter to operate than Temporal. Virtual objects would give per-project serialization for free — useful, since concurrent runs against one project are a live hazard today. Against it: younger ecosystem, smaller Python SDK, less proven at multi-hour activity durations.
Hatchet viable Postgres-backed, task-queue-first with DAG support and concurrency keys. Simpler to run than Temporal and genuinely container-agnostic. Weaker durable-code model — cyclic gate logic is less natural to express than in a workflow function.
DBOS wrong axis Near-zero infrastructure — durable execution in-process on Postgres. Very low migration cost and it would fix the crash-resume problem. But cross-machine per-step scaling is precisely its weak axis, and that's your actual requirement.
Argo Workflows ruled out by constraint Container-per-step gives genuine isolation and per-step resource requests, and it would have been a serious contender. But it is Kubernetes primitives — that's its entire scheduling model, which conflicts with your stated requirement. You'd also encode reloop and gate logic in YAML and lose the Python IR's fidelity.
Prefect / Dagster / Flyte poor fit Data-pipeline shaped. Acyclic assumptions, materialization semantics built for datasets, and no good story for a 45-minute wait on a human verdict.
Ray complement Compute fan-out, not durable orchestration. Could sit inside an activity for parallel eval sweeps — not a replacement for the control plane.

Sequencing

Migration phases

Prerequisites — do these regardless of engine

Pin prompt bundles by content hash. Make reads/writes accurate and enforced by a test that fails when a node touches an undeclared path. Give finalize and the selection merge idempotency keys (run_id + node_id). Move verdict parsing behind a clean boundary. Every one of these improves the current single-machine executor.

Durable interpreter, one queue, worker-affine

Temporal interpreter over the existing graph; all nodes as activities on a single queue with a sticky workspace. Behaviour-identical to today, but durable, resumable, and observable. Prove parity against --dry-run and the benchmark suite before anything else changes.

Split queues, per-role scaling

Task queue per role with independently sized worker pools. Derive RetryPolicy and timeouts from the existing AgentConfig entries. This is where the scale problem you opened with actually gets solved.

Child-workflow fan-out and artifact prefix

SubgraphForkNode becomes child workflows; the shared prefix moves to content-addressed artifacts per the hybrid workspace decision. Real human gates via signals. InnerLoop and optimize from #1051/#1052 become parent workflows here — and pre_eval/post_eval get deleted.

CEO as client; dashboard on history

Retrofit factory ceo against the gate API defined in phase 1. Dashboard reads workflow history rather than tailing events.jsonl. Retire checkpoint.py.

Needs your call

Open decisions

  • Self-hosted Temporal or Temporal Cloud? Self-hosting means running the server plus Postgres/Cassandra and Elasticsearch for visibility — real operational weight. Cloud removes that but puts run metadata off-premises, which given the Red Hat context may not fly. This materially affects whether Restate's single-binary story wins instead.
  • Do concurrent runs against one project need to be serialized? Today nothing prevents two cycles racing on the same .factory/ directory. If that guarantee matters, Restate's virtual objects give it natively; in Temporal it's a workflow-ID uniqueness policy you have to design.
  • Should #1051/#1052 land before or after the prerequisites? My read: land them, because they document what the outer loop needs. But agree now that CycleAnalyzer's implementation is provisional, so nobody builds more on the file-scraping path.
  • What's the deprecation criterion for the CEO path? Write it down in phase 1 or the two paths will coexist indefinitely.
If you only take one thing

The prerequisites are the whole gate. Accurate artifact declarations, deterministic gates, and idempotent finalize are what make retries safe — and until retries are safe, no orchestration engine can do anything for you except fail more expensively. They're also the changes that make the current executor better on their own, which makes them the lowest-risk work on this page.
